# L2 真实记忆人工验收单

这是一份待填写的验收模板，不是已通过的测试集，也不是可直接执行的配置文件。
现有 `run-direct-recall.mjs` 运行合成回归；真实样本需要先核对事实和精确证据引用，
再按同一输入进行召回。不要因当前实现返回了某条证据，就倒推它是预期答案。

## 每条样本需要确认的信息

| 项目 | 待填写内容 |
|---|---|
| 样本 ID | 自定义唯一编号 |
| 审核状态 | pending；人工核对完成后填 reviewed，并记录审核人/日期 |
| 用户问题原文 | 保留姓名、否定词、时间表达；如需脱敏，同步替换事实与实体别名 |
| 事实与真实来源 | 对应的记忆原文及来源引用，不填写猜测的原因 |
| 目标实体 | Entity id、version；同名时分别列出，不合并 |
| 访问范围 | owner/agent/session、允许的分享策略和敏感级别 |
| 查询时间 | 固定 referenceTime、UTC 偏移、knownAt 和预期 valid 时间范围 |
| 预期起点 | 精确 Claim id、version；无合格起点时写空 |
| 预期证据 | 允许返回的 Claim/Relation 精确引用；区分起点与路径中的其他人物 |
| 预期响应 | 有证据／证据不足／需要澄清／明确的接口错误 |
| 实际结果 | 原始 evidence、trace、错误码；记录代码版本、模型指纹与配置 |
| 判定及原因 | 通过或失败；缺失证据、误召回、身份混淆、时间错误等 |

如果无法确认 Entity 或 Claim 的精确引用，先保留 pending。无需把本机完整记忆库、
登录配置、API key 或加密密钥复制进仓库；只整理本次明确需要检查的材料。

## 建议先准备的六类场景

1. 同一个人的明确原文问题与口语改写：两种问法应指向同一组已核对的证据。
2. 两个人有相似经历：问题明确指定甲，乙的相似记录不能替代甲的起点。
3. 不同日期：甲只有昨天的记录，问今天时应证据不足；问昨天才返回对应记录。
4. 同名或共同别名：保留不同身份，不能自动合并或任意挑选。
5. 否定、计划、转述：区分“成功”“失败”“没有失败”“计划成功”“听说成功”；
   无法判断的表达应记录为待澄清，不能机械当作否定或肯定事实。
6. 来源或权限变化：删除/修改来源、撤销分享后，旧引用不能继续进入回答。

## 判读与复测

先冻结预期证据和查询时间，再运行。失败时按顺序检查：L1 是否合格、实体身份是否
明确、有效时间/权限是否允许、模型缓存是否完整、起点是否选错、关系是否已审核、
来源回读是否仍有效。预算错误与不支持的历史快照是错误，不能计作正确无答案。

同名歧义不等于检索失败：需要唯一身份的问题应澄清；仅要求列出候选时可分别给出
证据。沿已审核关系找到的其他人物可能是有效关联证据，不要把它与“用别人替代起点”
混为一谈。

分别报告真实人工样本、合成回归、模型探索结果。样本少时列出逐题结果与失败原因，
不宣称代表整体用户召回质量。修改后用相同数据版本、时间、权限和预期引用复跑。
